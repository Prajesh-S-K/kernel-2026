## 0.2.0 professional hardening

- Split responsibilities without adding parallel control algorithms or a JS framework. Read-only
  System views preserve existing readers; all accepted profile changes use validation.
- Typed faults drive logic. Readable reasons are presentation, not condition checks.
- Stop commands release before storage and before another sample. Failed delivery inhibits output;
  recovery requires consecutive healthy checks plus successful neutral delivery and explicit resume.
- Bound all transport waits; discard a failed native session rather than accepting a late stale reply.
  Persist trials separately from device commands. Finish telemetry lines before acknowledgement priority
  applies, so JSON lines cannot interleave.
- Freeze and group Lab context by block/settings. Identical temporary selection overrides make
  condition changes explicit; host-pointer smoke trials cannot establish adaptation benefit.
- Formatting/lint tools are pinned development dependencies. Gate stamps bind all source bytes and
  built artifact hashes; packaging refuses dirty/stale inputs. GPIOs and START parameters stay unchanged.

## Hands-free revision (unreleased)

| Decision | Reason / limit |
|---|---|
| Hands-free is a separate, versioned, checksummed two-slot record; the 84-byte profile is untouched | Existing profiles stay compatible; mode is never inferred from the profile |
| Missing record = legacy; corrupt/unsupported/out-of-bounds = CONFIG_INVALID (inhibited) | A damaged setup must not silently fall back to buttons or to an enabled mode |
| Conversion order: profile (dwell on) first, configuration record last as the single commit point; failures restore the profile | A hands-free setup is never partially enabled; interrupted saves are testable with a power-loss model |
| Gestures are generic stroke sequences trained per user, matched by a deterministic state machine; no classifier, no ML | Small, auditable, bounded; users choose comfortable patterns |
| Two commands only: pause/resume and drag toggle | Everything else stays dwell/pointer; fewer patterns to confuse |
| Patterns must differ and neither may be a prefix of the other | A prefix would fire early inside the longer pattern |
| A candidate suppresses pointer, scroll and dwell and its movement is discarded; neutral is required before re-arming | Prevents command motion from moving the pointer or replaying; costs up to about one stroke of pointing on a rejection |
| 2026-10-08 | No recognition threshold or timing is changed after the Lab block showed rejected candidates on keyboard pointing | Measured: candidates open only on sustained pitch+ / roll+ movement of about 20 deg/s or more after 300 ms of stillness, always end `TOO_SLOW` after 310 ms, cost 259-1035 px of movement at 20-60 deg/s, and execute nothing. Raising the entry rate only moves the cost to faster pointing and risks missing gentle gestures; shortening the stroke limit or ending suppression early changes safety-adjacent behaviour. Both need real gyro data first. See EVIDENCE "Pointing and rejected candidates" |
| Dwell lockout after resume and drag release | A user who is still after a gesture must not get a surprise click |
| Enable switch: OFF immediate, ON debounced 30 ms, unknown/unconfigured = OFF; ON never resumes | Fail closed; the switch permits, it is not a power switch |
| `setControlSwitch` is driven every loop pass, not per sensor sample | OFF must release without waiting for a sample |
| Alternative to a switch only by explicit helper qualification stored in the record | "Disabled switch configuration inhibits hands-free hardware mode" |
| Legacy physical-switch logic kept as a compatibility mode and test fixture, ignored in hands-free | Existing regressions stay valid |
| 2026-10-08 | The IMU driver identifies WHO_AM_I 0x68 (MPU-6000/6050) and 0x70 (MPU-6500) as distinct supported variants, rejects every other value without writing to it, reads back every configuration register it wrote, writes INT_ENABLE=0x01 on both and ACCEL_CONFIG_2=0x03 on the 6500 only, and never treats equal consecutive frames as a fault | The bench part answers 0x70 (MPU-6500 class), which the old strict 0x68 check rejected. Values come from RM-MPU-6000A-00 rev 4.0, RM-MPU-6500A-00 rev 2.1 and the MPU-6500 product spec rev 1.3 (mirror copies; TDK's site refused automated fetches). A still sensor produces identical frames, so equality is no freeze test (see the earlier timestamp-only freeze rule). On-hardware confirmation of the new init is pending |
| 2026-10-08 | A temporary movement-only demo mode exists (`handsfree demo on|off`): RAM-only, off at every boot, no dwell click/drag/wheel, 6 px per-report bound, enable input and all safety checks unchanged, changing it pauses control | A first look at the real assembly must not be able to click, drag or scroll the host; it must not alter the saved hands-free profile. The bound is a START value |
| 2026-10-08 | Hardware telemetry carries the raw sensor view (raw gyro/accel and per-axis gyro integrals) and the axis mapping can be set from MEASURED build flags (`NODX_GYRO_AXES/SIGNS`, `NODX_ACCEL_AXES/SIGNS`) | The START mount assumption must be replaced by measurement; `scripts/bench_axes.py` derives the mapping from a guided capture and refuses a capture that is not isolated or reliable |
| New protocol fields/commands are additive (`protocolRevision` 3, then 4 for the enable-input kind and raw/latched fields) | Existing clients keep working |
| 2026-10-08 | The enable input is one momentary push button by default (latch, never persisted, disabled at boot, held-at-boot ignored, stable release between presses, disabling press at its first edge, latch cleared by a fault); the maintained switch stays as an explicit stored option in flag bit 2 (clear = maintained) | The user's actual part is a four-pin momentary tactile button. A record written before the button existed keeps its original meaning byte-for-byte and is never reinterpreted; an older firmware reading the new bit fails closed. Disable at the first edge means a glitch can only disable control; a fault clearing the latch keeps the button from silently re-permitting after recovery |
| Version strings are not changed in this revision | Release/version handling is a separate task |
| 2026-10-08 | The temporary uncalibrated fallback is authorised by the explicit website start (no physical enable press); a button press only stops and revokes it. Configured/product-mode enable-button permission is unchanged. | Bench demonstration convenience, kept confined to the temporary demo; every other check stays |
| 2026-10-08 | The mounting guard blocks only above 75 degrees (warning above 35) and only at start | Gravity cannot tell a remount from head tilt; a tight guard would break ordinary use. Turns about the gravity axis stay undetectable and are documented |
| 2026-10-08 | One Euro START defaults changed to 1.5 / 0.05 / 2.0 after the first set failed the +30 ms stopping criterion on synthetic data | Criterion enforced in tests; hardware measurement still pending |
| 2026-10-09 | A quick tilt-and-return click (one practice tilt, integrated-angle state machine) is added next to, and mutually exclusive with, dwell and the trained gesture | The template training was too hard for the bench demo; everything is EXPERIMENTAL START, RAM only and off by default |
| 2026-10-09 | The quick gesture's alignment is a validated angular tolerance (default 30 degrees) around a signed designated direction learned by practice; deviation after the candidate starts cancels it at once | Only the chosen direction may click; opposite and perpendicular movements keep pointing normally |
| 2026-10-09 | A dwell action palette (Left, Right, Double, Drag, Scroll, Stop) is added as an explicitly enabled demo mode, mutually exclusive with dwell clicking and both gesture recognizers, driven by the existing SelectionManager and the SafetyManager -> HIDManager order | One dwell duration for every action; no per-action wait lengths. RAM only, off at every start and stop |
| 2026-10-09 | Palette selection is done by the device's dwell while the companion reports where the pointer is (a control, the bare palette window as `frame`, or outside); the completed dwell is consumed as a selection and never becomes an OS click | Fail closed: a target action needs a FRESH report that the pointer is outside the palette (the page repeats it; older than 2.5 s counts as missing and then nothing acts), a completed target dwell waits a 150 ms commit time that a palette entry can cancel, and entering the palette inhibits target actions before any selection. NOT guaranteed: a report delayed beyond about 1.6 s (dwell + commit) cannot be detected and a click can reach the target; the palette window having no click handlers is not a defence. The report path was measured (0.4 ms in software; median 105 ms, 95% 516 ms, worst 835 ms on the earlier real-board recording with two pollers) |
| 2026-10-09 | A drag's release dwell starts at once where the button went down (standing still releases it); entering the palette while dragging releases the button before any selection; releasing never needs a fresh report | A drag must always be endable without deliberate movement, and the held button must not wait on a selection |
| 2026-10-09 | Drop and Cancel are dwell-selected palette controls (no movement needed): Drop releases and returns to Left-click, Cancel also clears every pending or armed action. Entering the palette during a drag releases the button and the System confirms that the release report was delivered with the button up before any selection is possible | A failed or undelivered release must never be treated as released; release on entry means the button comes up over the palette, which is why Drop/Cancel exist as explicit, movement-free ends of a drag and why dropping on a target is done by dwelling there |
| 2026-10-09 | A separate, optional macOS overlay (AppKit through PyObjC, own virtual environment, one dependency) talks only to the existing companion bridge over HTTP; the firmware stays the single authority for target dwell actions, held-button state and the SafetyManager -> HIDManager -> BLE output | No second serial connection and no second mouse-injection path; the native dependency is kept away from the firmware and browser requirements. Tested with PyObjC 12.2.2 on Python 3.14 / macOS 27.0.1 |
| 2026-10-09 | The overlay times only its own menu dwell and sends validated `actions select`; the device times target dwells and consumes them while the pointer is on the overlay; exactly one controller (browser or overlay) owns the palette | One owner per dwell timer, so no action can run twice; the other controller's commands are refused |
| 2026-10-09 | "The pointer is on the overlay" is reported at once and repeated; it is acknowledged in the status; a lost report inhibits target actions after 2.5 s and switches the overlay controls off (releasing a held button) after 5 s; nothing resumes by itself | Fail closed. A click landing while the pointer is on the overlay hits the overlay window; this is documented as a physical effect, not as OS-wide click interception |
| 2026-10-09 | Overlay commands carry tokens: a claim names the current session serial and an epoch above every accepted one; menu, select, keyboard and release carry the claim's epoch; the overlay drops queued commands and ignores replies of an old epoch and claims above the device's reported epoch floor | A delayed, queued or in-flight command from an old overlay session (after a Stop, a timeout or a reconnect) must never reclaim the controls, reopen the menu or run an action. Not authentication: any local process can still use the bridge |
| 2026-10-09 | Keyboard mode is worded as "the keyboard's host process is running, NodX cannot see whether a keyboard is on screen", keeps a persistent recovery hint, ends by itself if the host quits, and the documentation states that leaving keyboard mode does not switch off the keyboard's own dwell (two click generators) | Process detection must not imply visibility; Cancel, Stop, Keyboard and any action stay reachable because the menu is timed by the overlay, not by NodX clicks |
| 2026-10-09 | The Keyboard item does not try to open the Accessibility Keyboard: macOS 27.0.1 offers no public way (it is hosted by the `Assistive Control` input method); it switches NodX into keyboard mode (target dwell clicks paused) only when the keyboard's host is running, otherwise it opens the Accessibility settings pane and shows one-time setup | No private APIs, UI scripting or posted key events; detection uses NSWorkspace and needs no permission, at the cost of seeing only that the host runs, not that its window is visible |

The per-report step bound is not scaled, so fast head movement is clipped even at 1x |
| 2026-10-09 | "Keep selected action" (off by default, off at every session start) keeps Right-click and Double-click selected after they run; it never applies to Drag or Scroll | Drag and Scroll must always need their own dwell to start; the option lives in the main page (the palette window has no click handlers) |
| 2026-10-09 | The palette window is compact (about 300 px wide), still an ordinary browser window, and the documentation states it cannot guarantee always-on-top behaviour | A native overlay was out of scope; the device stops acting if the window stops reporting |
| 2026-10-09 | One selection per hover: a chosen control is locked until the pointer leaves it | A resting pointer must not keep choosing the same action |
| 2026-10-09 | The page does not reset its report on window blur, only on a real exit, a hidden page or a closed page, and reports the whole page as the palette | A blur can happen while the pointer is still over the window; the window background is not a target |
| 2026-10-09 | Scroll is two-step (select, then dwell on the content to start; no click either time), freezes the pointer while active, and is left by holding BOTH axes still for the dwell time (the Exit control shows the progress); the website Stop and the physical button always stop it | A frozen pointer cannot travel to a control, so the exit cannot be a pointer dwell on a control.
